#+TITLE: Releasing
#+DATE: 2026-09-28
#+AUTHOR: dsp-dr

This plugin's version lives in one place: =version= in [[file:.claude-plugin/plugin.json][=.claude-plugin/plugin.json=]]. Raise it on every release --- the directory and =gh skill install --pin= both key off it.

** What counts as patch / minor / major
Semver, judged against what an installer of this plugin actually depends on: the skills' behavior and their =SKILL.md= contracts, =skills/*/scripts/*.sh= as a public interface, and the plugin manifest itself.

| Bump    | When                                                                                                                                                                                                                                                                      |
|---------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| *patch* | Wording/doc fixes in a =SKILL.md= or this repo's own docs; a =skills/*/scripts/*.sh= fix that doesn't change its arguments or output shape; adding a regression test; anything in =evals/= or the =evals/workspace/= benchmark output.                                        |
| *minor* | A new skill added; a new optional flag on a =skills/*/scripts/*.sh= script; a =SKILL.md= description or instructions change that widens /when/ it triggers or /what it covers/, without breaking an existing caller.                                                      |
| *major* | Removing or renaming a skill or a =skills/*/scripts/*.sh= script; changing a script's existing argument/output contract; changing the derived-port scheme in =guile-repl-paths.sh=; anything that would silently break someone who scripted against the previous version. |

When in doubt, look at it from =gh skill install dsp-dr/guile-skills <skill> --pin vX.Y.Z= --- a bump is major exactly when pinning the /old/ tag stops being a reasonable way to avoid the change.

** Cutting one
#+begin_src sh
gmake release-staging                    # regression tests + validate + dry-run, no publish
gmake release-production TAG=v0.2.0      # same gate, then the real `gh skill publish --tag`
#+end_src

=release-production= refuses to publish if the gate fails. It also drives the same =release:start= / =release:end= labels the CI gate uses (=.github/workflows/gate.yml=) when run against a PR --- apply =release:skip= to a PR to bypass the gate (e.g. a docs-only change), the same escape hatch =labeler:skip= gives the path labeler.

=gh skill publish= handles the GitHub side: it tags the release, adds the =agent-skills= topic if the token has admin on the repo, and prints the =gh skill install= / =--pin= commands for that version.

** Publishing from a merged PR

The path labeler applies *deployable* to any PR touching =skills/=,
=.claude-plugin/=, =scripts/lib/= or any other plugin component directory
(=monitors/=, =agents/=, =hooks/=, =commands/= and the rest listed in
=.github/labeler.yml=) --- the paths that decide what an installed
user receives. Merging a PR that carries that label publishes a release
(=.github/workflows/publish.yml=).

Those are the same paths =scripts/check-version-bump.sh= guards, so a deployable
PR is by construction one that had to raise =version= in =plugin.json= to pass
checks. The workflow publishes whatever version =plugin.json= names on =main=
after the merge, tagged =v<version>=.

- *To merge a deployable change without publishing*, remove the =deployable=
  label before merging.
- *If the tag already exists* the job stops rather than moving it. Tags are
  protected by the "Immutable release tags" ruleset, and a version that was
  already published is a bump that did not happen.
- The workflow runs the same gate a human runs locally --- =scripts/release.sh
  production=, which is tests, manifest validation, eval suites and
  =gh skill publish --dry-run= before the real publish.

* Branching and pushing

Publishing is automatic, so the /shape/ of a branch decides what ships. Four
rules, each here because it was gotten wrong at least once.

** One branch, one side of the deployable line

Never mix a change under =skills/=, =.claude-plugin/= or =scripts/lib/= with one
outside it. Merging the first kind publishes a release; merging the second kind
should be free. A change that has both halves is two branches, and the
non-deployable half can merge whenever.

The line is not intuition: =scripts/check-version-bump.sh main= names the shipped
files a branch touches, and answers with the label the PR will get. Run it before
opening anything.

** Pick the version against the published tags, not against =main=

=main='s version is the last one published. The next one is *not* simply
=main= plus a patch, because another open branch may already be holding that
number:

#+begin_src sh
git fetch --tags
git tag -l 'v*' | sort -V | tail -1     # the highest number that already exists
gh pr list --state open --label deployable \
  --json number,headRefName             # and the numbers being held
#+end_src

Choose strictly greater than both. A skipped number costs nothing --- nothing
reads the sequence for contiguity. A *colliding* number costs a failed publish
after merge: =publish.yml= stops rather than moving a tag, tags are immutable by
ruleset, and the fix is another bump and another merge.

=check-version-bump.sh= will not catch this. It only greps the diff for an added
=version= line, so two branches can both claim one number and both pass review.

** Rebase on =origin/main= before pushing, then check the version again

#+begin_src sh
git fetch origin
git rebase origin/main
git tag -l 'v*' | sort -V | tail -1     # did the number move while you worked?
gmake checks
scripts/check-version-bump.sh origin/main
#+end_src

The second version check is the point. A branch written against one =main= can be
rebased onto a =main= that published the number it was going to use.

** Push the notes; nothing else does

A =git note= is the repo's record of context, deviations and timeline, and it
lives on =refs/notes/commits=, which is *not* carried by =git push=, =--all=, or
=--follow-tags=:

#+begin_src sh
git push origin HEAD
git push origin refs/notes/commits      # separate, always
#+end_src

Two related traps, both real:

- *A rebase leaves the note behind*, attached to the pre-rebase sha, so the
  commit you push has none. Fix it once per checkout:

  #+begin_src sh
  git config notes.rewriteRef refs/notes/commits
  git config notes.rewrite.rebase true
  git config notes.rewrite.amend true
  #+end_src

  If a note is already stranded, =git notes copy <old-sha> HEAD= recovers it ---
  the old commit survives in the reflog.

- *Notes drift silently.* Nothing warns that the local ref is ahead:

  #+begin_src sh
  git ls-remote origin refs/notes/commits
  git rev-parse refs/notes/commits
  #+end_src

** No stacked deployable PRs

A PR whose base is another PR's branch gets no =checks= and no =gate=, because
both run only for PRs into =main=. Its =deployable= label and its version bump
are judged against a base that is not what users receive. So deployable changes
are never stacked. When several belong in one release, *fold* them: each PR
targets =main=, and a single release PR merges them in, carries the one bump at
the highest level of anything inside it, and is the one that publishes. That is
what 0.2.0 (#17, folding #8 and #12) and 0.4.0 (#26) did. =publish.yml= also
publishes only for PRs whose base is =main=, so a stack merged by mistake starts
no publish.

Non-deployable work (docs, CI, the model) may stack freely. Nothing publishes
for it.

** Folding PRs into one release PR

Merging a release PR that contains other PRs' merge commits marks each of them
merged, and GitHub fires =closed= for every one. Any that carried =deployable=
starts its own publish of the same =main=. For 0.4.0 that was #22 beside #26.
=publish.yml= therefore runs in one =concurrency= group, queued rather than
cancelled.

** Publishing is idempotent

=scripts/release.sh production TAG= can be rerun at any point.
=scripts/release.sh status TAG= names the state it will act on:

| state    | meaning                     | production does                                  |
|----------+-----------------------------+--------------------------------------------------|
| none     | no tag                      | gate, then =gh skill publish --tag=              |
| done     | tag at HEAD, release exists | nothing; exit 0                                  |
| resume   | tag at HEAD, no release     | gate, then =gh release create= from the tag      |
| conflict | tag on another commit       | exit 1: a bump that did not happen               |

After publishing it re-reads the state and fails unless it is =done=, so a
publish that claims success but leaves no release is caught. To finish a stuck
release, run the *Publish on merge* workflow by hand (=workflow_dispatch=); it
publishes the version =main= names, and does nothing if that is already done.
=tests/test-release-idempotency.sh= covers all four states with a stubbed =gh=.

** After the merge, confirm the release happened

Merging a =deployable= PR starts =publish.yml=; it is not proof the release
landed. Check all three, because they can disagree:

#+begin_src sh
git fetch --tags && git tag -l 'v*' | sort -V | tail -1
gh release list --limit 3
#+end_src

and the version the directory reports as live. A tag with no release, or a
release the directory has not picked up, is a real state --- not a delay to
assume away.

* Cutting one by hand
=gh skill= is a preview command that landed in *gh v2.90.0*. FreeBSD's ports tree lagged well behind it --- =pkg= offered 2.83.2 on 2026-09-28, which has no =gh skill= at all --- so v0.1.1 was cut by hand before the newer =gh= was built from source. [[file:CONTRIBUTING.org][CONTRIBUTING.org]] has the upgrade; once =gh skill --help= answers, =gmake release-production TAG=vX.Y.Z= is the supported path and this section is the fallback.

The manual sequence, which is the whole of it:

#+begin_src sh
./scripts/release.sh staging                 # gate: tests, validate, eval suites
                                         # (the publish step reports SKIPPED)
$EDITOR .claude-plugin/plugin.json       # bump "version"
git commit ... && git push origin main   # the directory reads the version here

git tag -a v0.1.1 -m "..." && git push origin v0.1.1
gh release create v0.1.1 --notes-file - <<'NOTES'
...
NOTES
#+end_src

Four things this does *not* do, each of which is easy to assume it did:

- *It does not publish to the plugin directory.* The directory tracks =main= and reads the version from =.claude-plugin/plugin.json=; the tag is a git artifact beside that, not the mechanism. The push is what the directory sees.
- *It does not clear review.* A listing held for content-policy review stays held, and with auto-publish off no version goes live without a reviewer.
- *It does not add the =agent-skills= topic.* =gh skill publish= would; check with =gh api repos/<owner>/<repo>/topics= and add it by hand if missing. It was already set here.
- *It does not print =gh skill install --pin= lines*, and it skips the Agent Skills spec validation that =gh skill publish= performs --- name rules, =name= matching the directory, required frontmatter, =allowed-tools= being a string rather than an array, and stripped install metadata. Run =gh skill publish --dry-run= separately if you cut a release by hand.

Two conventions worth keeping when doing it by hand: tag *annotated* (=-a=), so the tag carries who cut it and what the gate said --- =v0.1.0= is lightweight, which is the inconsistency this note exists to stop repeating --- and tag the exact commit that was gated rather than whatever =HEAD= has become since.
